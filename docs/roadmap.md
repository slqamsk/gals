# GALS — Техдолг и развитие

Этот файл — единая точка для всего, что **отложено**: технический долг (как код должен быть устроен) и список улучшений (как систему развивать). В будущем, при накоплении, планируется разделить на два отдельных файла — `tech_debt.md` и `improvements.md`.

## Принципы работы с этим файлом

*   **Один пункт — одна проблема.** Не сваливать в кучу «и рефакторинг, и новую фичу».
*   **Проблема + Решение.** Каждый пункт описывает, *что не так* сейчас и *что планируется сделать*.
*   **Нумерация сквозная.** `TD-XX` — не переиспользуется. Если пункт закрыт — удаляется (номер не занимается заново).
*   **Приоритет — по мере появления.** Явные приоритеты не проставляются; порядок в файле примерно отражает важность.
* **Перед реализацией — обсуждение.** Если изменение затрагивает несколько файлов или логически сложное — сначала план, потом код (см. `readme.md`, промпт).

## Технический долг (как код должен быть устроен)

**TD-01: Внедрение Service Locator / Dependency Injection**
*   **Проблема:** Сквозная передача объекта `Database` через конструкторы всех вкладок (Prop Drilling) увеличивает связность.
*   **Решение:** Создать глобальный класс `AppContext` (Singleton), который инициализирует БД и репозитории. Вкладки будут запрашивать зависимости напрямую из контекста.

**TD-04: Агрегация нескольких типов активностей в одном индикаторе**
*   **Проблема:** Текущая схема (1 индикатор = 1 источник) не поддерживает агрегацию (например, калории за день из бега + прогулки). Также нет связи «одна обязанность → несколько типов активностей».
*   **Решение:** Добавить связь «многие-ко-многим» (`indicator_activity_types` или `duty_activity_types`) или хранить JSON-массив ID в `indicators`.

**TD-05: Модуляризация `../src`**
*   **Проблема:** Плоская структура папки (все файлы в корне).
*   **Решение:** Разбить на пакеты (`repos/`, `tabs/`, `services/`) при превышении порога в 100 файлов.

**TD-06: Рефакторинг `datetime_utils` в класс `DateTimeManager`**
*   **Проблема:** Модуль использует глобальную переменную (`_USER_TZ`) и требует ручного вызова `init_timezone()`. Веб-часть (`web_sync.py`, `web_events_service.py`, `tools_web_events_tab.py`) читает приватный `_USER_TZ` напрямую.
*   **Решение:** Обернуть логику в класс (Java-style). Заменить ручную передачу аргумента на авто-чтение файла `user_timezone.txt` при инициализации. Дать публичный доступ к таймзоне вместо обращения к приватной переменной.

**TD-07: Перевод всех SQL-запросов на именованные параметры**
*   **Проблема:** Использование позиционных параметров (`?`) требует строгого соблюдения порядка переменных.
*   **Решение:** Перевести все запросы во всех репозиториях на синтаксис `:param_name`. Новые репозитории уже пишутся так.

**TD-08: Настройка визуальных тем и отрисовка сетки таблиц**
*   **Проблема:** Стандартные темы `ttk` (vista, clam) не поддерживают отрисовку линий сетки в Treeview и выглядят устаревшими.
*   **Решение:** Внедрить библиотеку `ttkthemes` или аналогичную. Заменить вызов `style.theme_use()` на подходящую тему. Выбор темы вынести в `preferences`.

**TD-09: Универсальная топологическая сортировка таблиц при импорте**
*   **Проблема:** В `BaseExchangeService._sort_tables_for_import` жёстко задан словарь приоритетов. При добавлении новых таблиц его нужно вручную поддерживать. Таблицы `regular_duties`, `regular_duty_marks`, `web_time_events`, `units`, `measurement_*`, `questions`, `question_options`, `answers` уже пришлось вписать вручную. Уровни исправлены 2026-11-16: `web_time_events`=1, `regular_duties`=4, `activities`/`indicators`/`regular_duty_marks`=5, `answers`/`indicator_values`/`metric_values`=6 — до этого обязанности попадали в конец списка и импорт падал по FK.
*   **Решение:** Заменить словарь на топологическую сортировку по фактическим FK-зависимостям (через `PRAGMA foreign_key_list` и `graphlib`). Костыль со словарём уже покрывает все текущие таблицы.

**TD-11: Рендеринг Markdown-документации прямо в приложении**
*   **Проблема:** Вкладка «Техдолг» сейчас просто отображает сырой текст `.md`-файла в `Text`-виджете, без форматирования.
*   **Решение:** Подключить легковесную библиотеку для рендеринга Markdown в `Text` (например, `tkhtmlview` или кастомный парсер), чтобы заголовки и списки выглядели красиво.

**TD-13: Нелинейное агрегирование satisfaction**
*   **Проблема:** Итог метрики считается как линейное средневзвешенное `Σ(score·weight)/Σweight`. Из-за этого один индикатор с 0% при весе 100 из двух (сумма весов 200) даёт итог 50%, а не «почти ноль».
*   **Решение:** Ввести нелинейное агрегирование (например, среднее геометрическое, `α·min + (1−α)·mean`, штраф за разброс `mean − k·std` или `mean(score^p)^(1/p)` с `p>1`). Отложено на релизы 3–4.

**TD-15: Вынос layout-логики графиков в общий модуль**
*   **Проблема:** `chart_tab.py` и `chart_metrics_tab.py` содержат дублированный код: `_is_overlap`, `_distribute_in_corner`, `_distribute_in_rect`, `_place_on_edge_zone`, `_draw_canvas` (логика зон и спирали). При изменении алгоритма позиционирования нужно править два файла.
*   **Решение:** Вынести общую layout-логику в `src/chart_layout.py` (функции `place_items(items, canvas_w, canvas_h, ...) -> None`, мутирующие `item["draw_x"]/["draw_y"]`). `chart_tab` и `chart_metrics_tab` будут вызывать одну функцию. `chart_tab.py` — легаси, но пока жив, дублирование сохраняется.

**TD-16: Защита веб-API `/z/` от несанкционированного доступа**
* **Проблема:** API-ключ `test-key-12345` лежит открытым текстом в `../z/index.html` и в `.env` на сервере. Любой, кто узнает URL `https://slqa.ru/z/`, увидит ключ и сможет читать/удалять события сна через API. Сейчас защита — только «никто не знает URL». Также в `z/api/.htaccess` стоит `Access-Control-Allow-Origin: "*"`.
* **Решение:**
    * Включить **HTTP Basic Auth** на папку `../z` (`.htpasswd` + `AuthType Basic`).
    *   Сузить CORS до `https://slqa.ru`.
    *   Сгенерировать настоящий случайный API-ключ (`openssl rand -hex 32`).
    *   Проверить редирект `http://` → `https://`.
* **Отложено** до момента, когда к веб-API будет постоянный доступ с телефона.

**TD-17: Внедрение автотестов (pytest + временная SQLite)**
*   **Проблема:** Инфраструктуры тестирования нет. Любая правка в `ScoreCalculator`, `IndicatorCalculator`, `PeriodRepository`, `IndicatorService.recalculate_for_date`, `web_events_service` проверяется только вручную. Особенно уязвимы:
    *   семантика GALS-дней и полуинтервал `[fact_start, fact_end)`;
    *   правило «один ночной сон на календарную дату окончания» (миграция 014);
    *   сон через полночь и границы `fact_end(X−1)` = начало сна, заканчивающегося в `X`;
    *   дедупликация web-событий и создание сна (sleep=последнее, wake=первое);
    *   математика `ScoreCalculator` (MAXIMIZE/MINIMIZE/TARGET/BINARY, `TIME_OVERNIGHT`);
    *   валидация week/month (пустой vs. «битый» день);
    *   расчёт по осям (`affects`) — средневзвешенное раздельно, вес 0, метрика без индикаторов (0/0);
    *   атомарность миграций (откат при падении в середине скрипта).
*   **Решение:**
    *   Ввести `pytest` как dev-зависимость (`requirements-dev.txt`).
    *   Фикстура `db` — временный файл SQLite в `tmp_path`, миграции через `Database.init_db()`.
    *   Изолировать `datetime_utils` (фикстура с фиксированным «сейчас»).
    *   Начать с юнит-тестов `ScoreCalculator` и `PeriodRepository`.
    *   Затем — интеграционные тесты `IndicatorService.recalculate_for_date`.
*   **Срок:** релиз 2.

**TD-18: Хардкод `+03:00` в триггерах `updated_at`**
*   **Проблема:** Часовой пояс в системе — настройка `user_timezone_offset` (сейчас `+3`). Но в триггерах SQLite (миграции `005`, `006`, `007`, `009`, `011`, `012`, `013`) литерал `+3` зашит жёстко: `strftime('%Y-%m-%dT%H:%M:%S+03:00', 'now', '+3 hours')`. SQLite-триггеры не могут прочитать `preferences`, поэтому в БД возможно расхождение: `datetime_utils.get_now_iso()` пишет с актуальным offset, триггеры — с `+03:00`. Если `user_timezone_offset` когда-нибудь изменится, в одной таблице окажутся записи с разными offset, и сортировка по строке ISO 8601 начнёт работать некорректно.
*   **Затронуто (шире, чем триггеры):**
    *   Триггеры `update_*_timestamp` во всех миграциях; косвенно — все репозитории, которые делают UPDATE.
    *   UI-диалоги, собирающие ISO-строку вручную: `manual_activities_tab.py` (пикер даты-времени и «Добавить активность»), `regular_duty_marks_tab.py` (добавление и редактирование активности), `measurements_input_tab.py`, `questionnaires_mark_tab.py`, `questionnaires_history_tab.py` (границы фильтров «Сегодня»/«Вчера»/«За N дней»).
    *   `period_repo.py` — все календарные границы (`get_or_create` для week/month, `_calc_day_bounds`, `_calc_aggregate_bounds`) и `activities_repo.get_all()` (fallback, когда day-периода ещё нет).
    *   Веб-часть offset не хардкодит, но читает приватный `datetime_utils._USER_TZ` — см. TD-06.
*   **Решение:** пока не исправлять (осознанное решение). Фиксированный `+03:00` в ISO считать частью контракта БД. При смене пояса потребуется синхронная правка UI, `period_repo` и пересоздание триггеров.

**TD-19: Фрагментированный ночной сон при инсомнии**
*   **Проблема:** Миграция 014 запрещает более одного «Ночного сна» на календарную дату окончания. Разорванный сон (лёг 23:00 → проснулся 02:00, снова лёг 02:30 → встал 07:00) нельзя внести двумя активностями: вторая запись отклоняется БД. Обход — объединять в одну активность 23:00–07:00 (пробуждения позже отражать в `breaks_duration`).
*   **Решение:** При появлении реальной потребности — либо разрешить несколько снов на дату с явным выбором сна-разделителя, либо моделировать пробуждения как перерывы внутри одного сна. Сейчас считаем, что фрагментированного сна нет.
*   **Отложено** до появления реальных данных.

**TD-20: Вечерний сон типом «Ночной сон» обрезает день**
*   **Проблема:** Сон-разделитель определяется по дате окончания. Если внести вечерний сон 19:00–23:00 типом id=1 и за эту дату нет настоящего ночного сна, он станет разделителем: `fact_start` = 19:00, день обрежется, утренние активности уйдут в предыдущий день. Если настоящий сон за дату уже есть — индекс 014 отклонит запись. Алгоритм это не проверяет: отсечек по времени начала (18:00 / 12:00) сознательно нет.
*   **Решение:** Дисциплина ввода — вечерний/дневной сон записывать отдельным типом («Дневной сон»). Если будет промахиваться — добавить валидацию (минимальная длительность или окно начала), но это возврат к отсечкам, от которых отказались.
*   **Отложено** до первого реального случая.

**TD-21: Под-роли мапятся по имени, а имя не уникально**
*   **Проблема:** В `sub_roles` нет `UNIQUE(parent_role_id, name)` — можно создать одинаковые имена под-ролей у разных ролей и даже две одинаковые у одной роли. При этом `activity_types_tab.py`, `manual_activities_tab.py` и `regular_duties_tab.py` строят словарь `sub_roles_map = {name: id}` сразу по всем ролям. Одинаковые имена затирают друг друга: выбор «Утро» для «Здоровья» может записать `sub_role_id` от «Работы», а триггер БД молча подставит чужую роль. Ошибки при этом не возникает.
*   **Решение:** Добавить `UNIQUE(parent_role_id, name)` (миграция, с предварительной проверкой существующих дублей) и мапить под-роли по паре (роль, имя) либо по ID. В picker-ах показывать контекст роли.
*   **Отложено** до появления реальных дублей или до ближайшей правки этих вкладок.

**TD-22: Score индикатора не хранится в истории**
*   **Проблема:** В `indicator_values` сохраняется только `actual_value`. Оценка 0–100 % нигде не хранится: `IndicatorService` считает её при пересчёте и сразу усредняет в `metric_values`, а окно «Метрика: {name}» считает заново из **текущих** параметров индикатора. После правки цели/шага/штрафа/веса окно показывает не те оценки, которые были учтены в сохранённой точке графика — историю нельзя воспроизвести.
*   **Решение:** Добавить `indicator_values.score` (миграция), заполнять при пересчёте, в окне читать сохранённое значение вместо повторного расчёта.
*   **Отложено** (осознанное решение: оставить как есть, помнить про расхождение).

**TD-23: Валидация порядка времени в «Ручной работе» и минутная активность**
*   **Проблема:** Пикер даты-времени (двойной клик по «Начало»/«Конец» в таблице «Ручной работы») задаёт даты независимо и не проверяет, что конец не раньше начала — `_save_row` пишет в БД как есть. При `end_time < start_time` метод `calc_duration` даст отрицательную длительность и испортит метрику. Отдельно: в диалоге «Добавить активность» равные времена начала и окончания по-прежнему запрещены, хотя по договорённости они должны означать активность длительностью 1 минута (например, короткий важный звонок).
*   **Решение:** Добавить в `_save_row` проверку `end < start` (ошибка + откат через `refresh_table`). Для минутной активности договориться о хранении: либо `end_time = start_time + 1 минута` на границе записи, либо `end_time = start_time` с трактовкой «1 минута» в коде расчёта. Второе требует отдельного учёта в проверках пересечений.
*   **Отложено** до следующей правки `manual_activities_tab.py`.

**TD-24: Избавиться от Smart UI (вынести бизнес-логику из `*_tab.py`)**
*   **Проблема:** Вкладки (`*_tab.py`) смешивают интерфейс и бизнес-логику сценария. Из-за этого сценарии нельзя тестировать без UI, переиспользовать и эволюционировать отдельно. Часть логики уже вынесена в сервисы (`indicator_service`, `web_events_service`, `web_sync`, `excel_service`, `json_service`), но многие операции CRUD, валидация и вычисления остаются внутри вкладок.
*   **Решение:** Вынести сценарии из вкладок в сервисный слой; вкладки оставить тонкими (виджеты + вызовы сервиса + отображение). Связано с TD-01 (Service Locator упростит внедрение сервисов в вкладки) и TD-17 (нужны тесты, чтобы гарантировать сохранение поведения при рефакторинге).
*   **Отложено** до релиза 3+.

**TD-25: Настроить formatter / linter (ruff)**
*   **Проблема:** В `requirements.txt` нет formatter/linter-инструментов. Стиль поддерживается вручную, единообразие не гарантировано. На момент создания проекта инструменты были неизвестны автору.
*   **Решение:** Добавить `ruff` (format + lint) в dev-зависимости (`requirements-dev.txt` или отдельный блок в `requirements.txt`), конфиг — в `pyproject.toml` или `ruff.toml`. Прогнать `ruff format` и `ruff check --fix` по `src/` одним коммитом (в истории git будет крупный diff — предупредить). В перспективе — pre-commit hook. Связано с TD-17 (CI для тестов и линтера).
*   **Отложено** до релиза 2.

## Список улучшений (как систему развивать)

**IMP-01: Внедрение подходов OKR**
*   **Проблема:** В системе нет сущности «Цель» (Objective), которая отделяла бы качественное направление от измеримых результатов. Периоды ограничены `day`/`week`/`month` — нет `quarter`, `year`.
*   **Решение:** Ввести `objectives` (качественная цель, цикл через `period_id`, опциональная иерархия `parent_objective_id`). Добавить `indicators.objective_id`. Расширить `MetricType` типами `quarter`, `year`, `five_year`. UI: вкладка «Цели». Семантика: индикатор может быть KPI (поддержание нормы) или KR (амбициозный рывок) — роль в контексте, не свойство схемы.
*   **Отложено** на релиз 3–4.

**IMP-02: Модуль планирования для задач с плавающей целью**
*   **Проблема:** Для некоторых активностей цель меняется от недели к неделе. Фиксированный `target_value` в индикаторе не подходит.
*   **Решение:** Модуль планирования с привязкой плана к периоду (график «план vs факт», процент выполнения плана). Цели на период хранятся отдельно (`indicator_plans` или аналог).
*   **Отложено** до появления реальной потребности.

**IMP-03: Список web-событий в UI (read-only)**
*   **Проблема:** Накопленные `web_time_events` видны только в SQLite. В UI их нет.
*   **Решение:** Read-only таблица (`tksheet`) в подвкладке «Web-события» или отдельной подвкладке «Журнал web-событий»: `id`, `server_event_id`, `event_type`, `event_time`, `processed`. Опционально — фильтры.
*   **Отложено** до накопления достаточного количества событий.

**IMP-04: Улучшение алгоритма дедупликации web-событий**
*   **Проблема:** Текущий алгоритм: `sleep` = последнее событие кластера, `wake` = первое. На реальных данных может потребовать корректировки: например, если пользователь лёг в 23:00, встал в 02:00 (в туалет), снова лёг в 02:05, встал в 07:00 — текущий алгоритм возьмёт 02:05 как «отбой».
*   **Решение:** Более сложный алгоритм: искать самую длинную пару `sleep`–`wake` в окне, отбрасывать «ночные пробуждения» (пары короче N минут). Параметры — в `preferences`.
*   **Отложено** до появления реальных данных, где текущий алгоритм даст сбой.

**IMP-05: Реализация `calc_count` для индикаторов по обязанностям**
*   **Проблема:** Сейчас для обязанностей доступны `calc_duty_done` (BINARY) и `calc_duty_mark`. Нет `calc_duty_count` — «сколько раз за период обязанность была отмечена».
*   **Решение:** Добавить `calc_duty_count` в `indicator_calculator.py`.
*   **Отложено** до появления потребности.

**IMP-06: Расширение измерений до compound-сеансов / batch_id**
*   **Проблема:** Сейчас compound-измерения (давление, обхваты) моделируются нативно: 1 сеанс + N значений по компонентам. Это работает, но для «средний балл по систоле за месяц» нужен JOIN `measurement_values → measurement_components` (одна `WHERE component_id = X`). Для будущих сценариев (аналитика по сеансу целиком, кросс-проверки «диастола < систола») механика уже покрыта схемой. Открытый вопрос — если понадобится «несколько `measurement_values` на один компонент в одном сеансе» (редкий кейс) или «частичный сеанс» (не все обязательные компоненты) — потребуется доработка.
*   **Решение:** Не требуется на текущем этапе. Добавить, если появится реальная потребность (например, «пульс до/после нагрузки»).
*   **Отложено.**

**IMP-07: Метрики по измерениям и ответам через индикаторы**
*   **Проблема:** Индикаторы уже умеют читать из `questions` (`calc_question_last`), но не из `measurement_values`. Для метрик на основе измерений (например, «Средний вес за неделю») нужно добавить `calc_measurement_*` методы и UI.
*   **Решение:** Добавить `calc_method` для измерений (`calc_measurement_last`, `calc_measurement_avg`, `calc_measurement_count`), поле `measurement_component_id` в `indicators`, UI в `indicator_config_tab.py`. Это 4-й источник.
*   **Отложено** до появления потребности.

**IMP-08: Отдельный алгоритм вычисления длительности активности**
*   **Проблема:** Сейчас `calc_duration` считает `end − start`, а поля `duration`, `clean_duration`, `breaks_duration`, `engagement_percentage` в математике не участвуют. С 2026-11-16 они хранятся только если пользователь ввёл значение вручную (иначе NULL) и показываются в UI как есть. Веб-часть (`web_events_service.py`) пока пишет вычисленную длительность — под общее правило NULL не приведена (подсистема законсервирована).
*   **Решение:** Отдельный алгоритм, который учитывает и введённую длительность, и `start`/`end`, допускает их расхождение и по правилам выбирает подходящее значение (правила уточнить: приоритет ручного ввода, учёт перерывов и вовлечённости). Заодно привести `web_events_service` к правилу NULL.
*   **Отложено** до формулировки правил.
