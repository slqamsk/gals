# GALS — Архитектура системы

## 1. Философия и принципы

*   **GALS** (ранее P&R) — персональная система управления жизнью.
*   **Главный принцип:** Система помогает достигать результатов, не требует обслуживания ради обслуживания. Учет ради учета запрещен.
*   **Девиз на «Главной»:** «Меньше учёта — больше результата».
*   **Развитие:** Agile-подход. От простого MVP к сложным механизмам. Отложенные задачи фиксируются в Техдолге.

## 2. Терминология и слои

Система строго разделена на три слоя:

1.  **Actions (Факты)** — сырые данные реальности. Несколько источников:
    *   **Активности (`activities`)** — например, *«Я спал с 23:00 до 07:00»*. Фиксируются вручную или из web-событий. Могут быть привязаны к **регулярной обязанности**.
    *   **Регулярные обязанности (`regular_duties` + `regular_duty_marks`)** — «надо делать с заданной частотой», закрывается явной отметкой (`done`/`not_done`/`partial`).
    *   **Измерения (`measurement_*`)** — объективные числовые факты «в момент T». Единица измерения привязана к компоненту; конверсии между единицами нет (пользователь пересчитывает сам). Compound-измерения (давление, обхваты) моделируются как один сеанс с несколькими компонентами.
    *   **Опросы (`questions` + `answers`)** — субъективные оценки. Каждый ответ — самостоятельный факт «в момент T» (без сеансов). В `answers` хранится **снимок** значения и описания варианта на момент ответа: переименование варианта в `question_options` не ломает историю.
    *   **Web-события (`web_time_events`)** — сырьё «Подъём»/«Отбой» из веб-API; из них по команде может быть создана активность «Ночной сон».

2.  **Indicators (Индикаторы)** — правила измерения (например: *«Длительность сна, цель 480 мин»*). Опираются **ровно на один** источник: `activity_type_id` ИЛИ `regular_duty_id` ИЛИ `question_id`. Имеют цель (`target_value`) и **ось влияния (`affects`)**: `satisfaction` (удовлетворённость результатом, ось X) или `attention` (вложение усилий, ось Y).

3.  **Metrics (Метрики)** — контейнеры контекста. Собирают в себе Индикаторы и выдают итоговые значения по двум осям (attention и satisfaction).

**Регулярная обязанность (Regular Duty)** — периодическое действие, которое надо выполнять с заданной частотой (раз в день / неделю / месяц). Может требовать нескольких сеансов-активностей до финального закрытия. Закрывается **явной отметкой** о выполнении (`regular_duty_marks`).

**Контекст метрики:** роль или под-роль. Метрика = (роль/под-роль + тип периода). Одна и та же роль может иметь несколько метрик с разными периодами (`day`, `week`, `month`, `manual`).

**Измерение (Measurement)** — объективный числовой факт, привязанный к **компоненту** типа измерения. Один сеанс содержит одно или несколько значений (по числу компонентов). Единица измерения задаётся на уровне компонента один раз (в UI — справа от поля ввода).

**Опрос (Question / Answer)** — субъективная оценка по вопросу с вариантами ответа (0–100). Каждый ответ — самостоятельный факт. Вопрос может быть привязан к роли / подроли (опционально) или быть общим (без привязки).

**Итоговые оси на графике:**
*   **Вовлеченность (Attention)** — сколько внимания уделено (ось Y). Считается средневзвешенным по индикаторам с `affects='attention'`. Если таких индикаторов у метрики нет — 0.
*   **Удовлетворенность (Satisfaction)** — насколько хорош результат (ось X). Считается средневзвешенным по индикаторам с `affects='satisfaction'`. Если таких индикаторов у метрики нет — 0.

> *Термин «Stats» временно выведен из обихода и будет заменён/переименован.*

**Статус расчёта по типам периодов:** расчёт реализован для метрик типов `day`, `week`, `month`. Тип `manual` автоматически не рассчитывается — такие метрики заполняются вручную, `recalculate_for_date()` их пропускает.

**Внешние источники активностей.** Помимо ручного ввода, активности могут появляться из **веб-API** (`https://slqa.ru/z/api`) — события «Подъём»/«Отбой», которые пользователь отмечает с телефона, когда компьютер выключен. Они складываются в `web_time_events`, а затем (по явной команде из UI) из них может быть создана активность «Ночной сон». Подробнее — раздел 6 (вкладка «Web-события») и раздел 3 (`web_time_events`).

## 3. Архитектура БД (SQLite)

* **Миграции:** Строгие `.sql` файлы (001, 002 и т.д.). Применяются по `PRAGMA user_version`. Каждая миграция выполняется **атомарно**: один скрипт = одна транзакция вместе с `PRAGMA user_version`, падение в середине откатывает её целиком и не сдвигает версию. На время применения внешние ключи выключаются на соединении (внутри транзакции `PRAGMA foreign_keys` не работает) и включаются обратно после. **Автобэкапа нет** — копию `../data/gals.db` перед новыми миграциями пользователь делает сам.
* **Защита данных:** Везде используется `ON DELETE RESTRICT` (запрет удаления родителя, если есть зависимые данные). Единственное исключение — `measurement_values.measurement_session_id`: `ON DELETE CASCADE` (значение без сеанса бессмысленно). Индикатор или вопрос с историей значений удалить нельзя — это осознанное поведение, архивации пока нет.
* **Ленивое создание:** Периоды создаются только в момент появления активности или ручного пересчета.
* **Минутная точность (MVP):** `start_time`/`end_time`/`created_at`/`measured_at` сохраняются с точностью до минуты. Секунды обнуляются в коде (`datetime_utils.to_minute_iso`) на границе записи в БД (`ActivitiesRepository.add/update`, `MeasurementsRepository.add_session/update_session`, `QuestionsRepository.add_answers_batch/update_answer`).
* **Длительности — только введённое:** `duration`, `clean_duration`, `breaks_duration`, `engagement_percentage` хранятся, только если пользователь ввёл значение вручную; иначе NULL (DEFAULT в схеме есть, но репозитории всегда передают значения явно). В математике эти поля не участвуют — `calc_duration` считает `end − start`. В UI пустое значение показывается пустым, а не нулём. Отдельный алгоритм, учитывающий и введённую длительность, и время, — в IMP-08.

### Основные таблицы:
*   `preferences` — настройки приложения (key-value в JSON).
*   `roles`, `sub_roles` — иерархия сущностей (с цветами).
*   `activity_types` — справочник действий.
*   `activities` — факты действий (время, опциональный `regular_duty_id`, nullable-длительности).
*   `periods` — временные периоды (включая фактические границы `fact_start`/`fact_end`).
*   `metrics` — реестр (связь роли/подроли с типом периода).
*   `regular_duties` — справочник регулярных обязанностей (что надо делать и как часто).
*   `regular_duty_marks` — отметки о выполнении обязанностей (транзакционная).
*   `indicators` — правила (цели, шаги, штрафы, веса, ось). Опираются **ровно на одно**: `activity_type_id` ИЛИ `regular_duty_id` ИЛИ `question_id`.
*   `indicator_values` — сырые факты за период (`actual_value`; оценка score не хранится — см. TD-22).
*   `metric_values` — итоговые проценты для графика (attention и satisfaction раздельно).
*   `web_time_events` — события «Подъём»/«Отбой», синхронизированные с веб-API (транзакционная).
*   `units` — справочник единиц измерения (seed 8 записей при первом применении миграции `011`).
*   `measurement_types` / `measurement_components` / `measurement_sessions` / `measurement_values` — подсистема измерений (EAV).
*   `questions` / `question_options` / `answers` — подсистема субъективных оценок.

### Регулярные обязанности и отметки

**`regular_duties`** — справочник:
*   `name` (UNIQUE), `description`
*   `activity_type_id` (FK, NOT NULL) — тип активности, которым выполняется
*   `period_type` (CHECK `day`/`week`/`month`) — за какой период надо выполнить
*   `role_id`, `sub_role_id` (оба nullable; `role_id` автозаполняется из `sub_role_id` триггером — как в `activity_types`)
*   `execution_order` (INTEGER NULL), `importance` (INTEGER NULL) — порядок и важность (миграция 010, без DEFAULT и без CHECK)

**`regular_duty_marks`** — транзакционная:
*   `duty_id`, `period_id`, `marked_at`
*   `status` (`done`/`not_done`/`partial`) + `mark_value` (0..100) + CHECK на согласованность:
    *   `done` → `mark_value = 100`
    *   `not_done` → `mark_value = 0`
    *   `partial` → `mark_value` в 1..99
*   Без `UNIQUE(duty_id, period_id)` — за период можно отметить несколько раз (история сохраняется)

**`activities.regular_duty_id`** — опциональный FK на `regular_duties`. Привязка сеанса к обязанности. Триггер проверяет совпадение `activity_type_id` активности с `regular_duties.activity_type_id`; подстановка типа при выборе обязанности — в UI и импорте.

### Измерения (EAV)

**`units`** — справочник единиц (display_name UNIQUE, full_name, description). Seed 8 записей: кг, см, мм рт. ст., уд/мин, %, ммоль/л, шт, руб. Пользователь может редактировать, добавлять, удалять (при отсутствии ссылок из `measurement_components`).

**`measurement_types`** — типы («Вес», «Давление», «Накопления»). `name` UNIQUE.

**`measurement_components`** — компоненты типа («Систола», «Диастола», «Пульс»). `UNIQUE(measurement_type_id, name)`. `unit_id` NOT NULL (FK на `units`). `display_order` (порядок в форме), `is_required` (обязателен ли в сеансе).

**`measurement_sessions`** — сеанс (когда и что измерили). `measurement_type_id`, `measured_at`, `notes`.

**`measurement_values`** — значения (числа). `measurement_session_id` (CASCADE), `measurement_component_id` (RESTRICT), `value REAL`. `UNIQUE(measurement_session_id, measurement_component_id)`.

### Опросы (субъективные оценки)

**`questions`** — вопросы. `text`, `role_id` (nullable), `sub_role_id` (nullable). Оба могут быть NULL — «общий» вопрос, доступен любой роли.

**`question_options`** — варианты ответа. `question_id` (RESTRICT), `value INTEGER` (0..100, CHECK), `description` NOT NULL. `UNIQUE(question_id, value)`.

**`answers`** — ответы (без сеансов). `question_id` (RESTRICT), `value INTEGER` (0..100) — **снимок** `value` варианта, `option_description` — **снимок** `description` варианта, `extra_comment` (nullable), `measured_at`. Снимок защищает историю от переименования варианта.

### Web-события (синхронизация с веб-API)

**`web_time_events`** — транзакционная:
*   `server_event_id` (INTEGER, UNIQUE) — id события на сервере (для идемпотентности при повторной синхронизации)
*   `event_type` (CHECK `wake`/`sleep`) — «Подъём» или «Отбой»
*   `event_time` (TEXT, ISO 8601, UTC+3)
*   `processed` (INTEGER 0/1) — 0 = ещё не использовано для создания активности; 1 = обработано (помечается кнопкой «Добавить сон», либо вручную через «Пометить все как обработанные»)
*   `created_at`, `updated_at`

**Логика синхронизации (`web_sync.py`):**
1. `GET /z/api/events/` — забрать все события с сервера.
2. `INSERT OR IGNORE` в `web_time_events` по `server_event_id` (повторный приход не создаёт дубль).
3. `DELETE /z/api/events/{id}` для каждого события на сервере.

**Без дедупликации и без удаления локально.** Всё как пришло — сохраняется.

**Логика создания сна (`web_events_service.py`):**
1. Окно `[D-1 H:00, D H:00)` по UTC+3, где `H = web_events_sleep_window_start_hour` (по умолчанию 18). Это окно используется **только** в веб-подсистеме; расчёт границ дня его не использует.
2. Взять **необработанные** (`processed = 0`) события в окне. Если в окне пусто — в сообщении об ошибке перечисляются необработанные события **вне окна** (пользователь мог не сменить дату).
3. **Предпроверка:** события каждого типа (`sleep`/`wake`) должны укладываться в окно `web_events_dedupe_window_sec` от **первого** события своего типа. Если нет — ошибка с полным списком событий типа.
4. **Дедупликация (в пределах окна):** `sleep` — оставляем **последнее** событие кластера (реальный отбой); `wake` — **первое** (реальный подъём). Окно кластера считается от первого события (`last_time` не сдвигается при замене sleep-события).
5. `start` = последний `sleep`; `end` = первый `wake` после него (строго позже).
6. Проверки: `end > start`; за `D` ещё нет активности «Ночной сон».
7. Создать активность `activity_type_id = 1` («Ночной сон»), `source = "web_events"`, заметка с id исходных событий. Длительность здесь пока вычисляется и пишется (подсистема законсервирована, под правило NULL не приведена — IMP-08).
8. Пометить **все** события в окне как `processed = 1`.

### Специальный тип активности "Ночной сон"

В таблице `activity_types` жестко зашит тип активности с `id = 1` и названием `"Ночной сон"`.
*   Его нельзя удалить или переименовать (защищено триггерами в БД).
*   Его наличие и название проверяется перед каждым расчетом индикаторов (Fail-Fast).
*   Если в базе нет записи о ночном сне за текущий день — пересчет индикаторов не запускается.
*   **Один сон в сутки:** в одну календарную дату может заканчиваться только один «Ночной сон» — частичный уникальный индекс по `substr(end_time, 1, 10)` для `activity_type_id = 1` (миграция `014`). Незавершённые сны (`end_time` NULL или `''`) в индекс не попадают. Ограничение действует на INSERT и UPDATE, включая импорт и правки через UI. Формулировка правила: «в одну календарную дату можно проснуться только один раз».
*   «Ночной сон» может быть создан **вручную** (в «Ручной работе») или **из web-событий** (в «Инструменты → Web-события → Добавить сон»).
*   **Ввод через полночь.** В диалогах добавления/редактирования одна дата на начало и конец — это осознанное ограничение диалогов. Сон 21:00 → 06:00 вводится так: создать активность с датой отбоя и пустым временем окончания, затем в таблице двойной клик по «Конец» и выбрать следующую дату. Пикер держит даты начала и конца независимо.
*   Вечерний/дневной сон (например, 19:00–23:00) нужно записывать **другим типом** активности. Если записать его типом «Ночной сон» и за эту дату нет настоящего сна, он станет разделителем и обрежет день — алгоритм это не проверяет (TD-20).

### Легаси-подсистема метрик

Таблицы `role_metrics` и `sub_role_metrics` (миграция `004`) сохранены как временный полигон для отладки UI старой вкладки «График метрик». Эта вкладка (`chart_tab.py`) не развивается и в будущем будет удалена вместе с таблицами.

## 4. Семантика периодов и активностей (Не календарные даты)

В системе **день — это не отрезок с 00:00 до 23:59**. Сутки начинаются с момента отбоя (ночного сна) и заканчиваются началом следующего ночного сна. Для этого в таблице `periods` добавлены поля `fact_start` и `fact_end`.

### Правила расчета границ дня:

1.  **`fact_start`** — время начала ночного сна (activity_type_id=1), который **закончился** в текущую календарную дату. Если такого сна нет (или он не внесен) — `00:00:00` текущей даты.
2.  **`fact_end`** — время начала ночного сна следующего дня. Если сон на следующий день еще не внесен — `23:59:59` текущей даты.
3.  Для периодов `week` и `month` фактические границы привязаны к крайним дням периода и (если он уже введён) к началу следующего периода:
    *   `fact_start(week)` = `fact_start(понедельник)` этой недели, если `day`-период понедельника существует; иначе календарное `понедельникT00:00:00+03:00`.
    *   `fact_end(week)` = `fact_start(следующий понедельник)`, если `day`-период следующего понедельника уже существует; иначе календарное `воскресеньеT23:59:59+03:00`.
    *   `fact_start(month)` = `fact_start(1-е число месяца)`, если он существует; иначе календарное `1-еT00:00:00+03:00`.
    *   `fact_end(month)` = `fact_start(1-е число следующего месяца)`, если он существует; иначе календарное `последнее числоT23:59:59+03:00`.

    Важное следствие: если понедельник (или 1-е число) пропущен, `fact_start` **не съезжает** на следующий доступный день — остаётся календарным. Так начало периода стабильно.

4.  **Автоматическое обновление границ вчерашнего дня.** При вызове `IndicatorService.recalculate_for_date(X)`:
    *   пересчитываются `fact_start/fact_end` для `X` (через `PeriodRepository.get_or_create`);
    *   пересчитываются `fact_start/fact_end` для `X−1`, если `day`-период `X−1` уже существует (`PeriodRepository.refresh_day_bounds_if_exists`; новый период **не создаётся**);
    *   затем обновляются `fact_start/fact_end` для всех `week`/`month`, содержащих `X` и (если вчерашний день существует) `X−1` (`refresh_aggregate_bounds`).

    Пункт про `X−1` важен, потому что `fact_end(X−1)` = начало ночного сна, заканчивающегося в `X`. Если сегодня внесли сон с началом в 05:00, `fact_end` вчерашнего дня должен стать `X T05:00:00`, а не оставаться старым.

    Для исправления накопленных расхождений (после удаления сна, импорта, ручных правок) во вкладке «Инструменты → Служебные операции → Проверить и скорректировать периоды» доступна разовая операция, которая пересчитывает `fact_*` для **всех** существующих `day`-периодов и `week`/`month`, логируя все изменения.

5.  **Порядок пересчёта при `recalculate_for_date(X)`:** сначала пересчитываются границы дней (X и X−1), затем недель, затем месяцев. Это нужно, чтобы родительские периоды видели актуальные границы входящих в них дней. После обновления границ индикаторы пересчитываются в том же порядке: день → неделя → месяц.

6.  **Валидация week/month.** Прежде чем считать индикаторы для недели/месяца, выполняется проверка:
    *   если внутри нет **ни одного** `day`-периода — расчёт пропускается с сообщением в лог («нет ни одного day-периода в диапазоне»);
    *   если хотя бы один существующий `day`-период **невалиден** (нет ночного сна или есть пересечение с ним) — расчёт пропускается с указанием проблемного дня;
    *   иначе — считается.

    Пустой день (day-периода нет вовсе) неделю не блокирует — это ожидаемое поведение. Блокирует именно «битый» день, у которого есть данные, но они некорректны.

### Правила принадлежности активностей:

*   Активность принадлежит периоду, если ее `start_time` попадает в полуинтервал: **`fact_start <= start_time < fact_end`**.
*   Благодаря этому ночной сон (например, с 23:00 до 07:00) относится ровно к одному дню. Двойного учёта (double-counting) не происходит.
*   Активность, которая началась до `fact_start` (например, пересекается с ночным сном), считается **ошибкой данных**. Перед расчетом индикаторов запускается валидация, которая ищет пересечения с ночным сном и блокирует расчет при их наличии. Проверка выполняется **при пересчёте**, а не при записи.
*   Два «Ночных сна» с одной датой окончания запрещены на уровне БД (миграция `014`), поэтому сон-разделитель для дня однозначен. `ORDER BY start_time ASC LIMIT 1` в расчёте границ сохранён как страховка для данных, внесённых до миграции.

**Измерения и опросы** принадлежат периоду по `measured_at` (аналогично активности — по `measured_at` из полуинтервала `[fact_start, fact_end)`).

## 5. Математика (ScoreCalculator)

Итоговая оценка индикатора (0–100%) рассчитывается на основе его параметров.

### Типы целей (`GoalType`):
1.  **`MAXIMIZE`** (Больше — лучше): Если факт ≥ цели — 100%. Иначе штраф за отклонение.
2.  **`MINIMIZE`** (Меньше — лучше): Если факт ≤ цели — 100%. Иначе штраф за отклонение.
3.  **`TARGET`** (Колокол): Штраф за отклонение в обе стороны от идеала.
4.  **`BINARY`** (Да/Нет): Факт > 0 — 100%, иначе 0%. Цель (`target_value`) для этого типа не требуется.

### Методы расчёта (`CalcMethod`):

По типу активности (`activity_type_id`):
*   **`calc_duration`** — сумма длительностей активностей этого типа за период (`end − start`; поле `duration` не используется).
*   **`calc_start_time`** — время начала самой ранней активности этого типа. `None`, если активностей нет.
*   **`calc_count`** — количество активностей этого типа за период.

По регулярной обязанности (`regular_duty_id`):
*   **`calc_duty_done`** — 1, если последняя отметка за период имеет `status='done'`, иначе 0. Для BINARY-индикаторов.
*   **`calc_duty_mark`** — `mark_value` последней отметки за период (0..100). Для MAXIMIZE/TARGET.

По вопросу (`question_id`):
*   **`calc_question_last`** — `value` последнего ответа за период (0..100) по `measured_at DESC`. `None`, если ответов нет. Для MAXIMIZE/TARGET.

Метод должен соответствовать источнику: для индикатора по типу активности — только `calc_duration`/`calc_start_time`/`calc_count`; по обязанности — только `calc_duty_done`/`calc_duty_mark`; по вопросу — только `calc_question_last`.

### Ось влияния (`affects`):
*   **`satisfaction`** — удовлетворённость результатом (ось X). Все индикаторы с этим значением идут в средневзвешенное по satisfaction.
*   **`attention`** — вложение усилий (ось Y). Все индикаторы с этим значением идут в средневзвешенное по attention.
*   Поле обязательно (`NOT NULL`, без DEFAULT). Для новых индикаторов пользователь обязан указать ось явно.
*   У одной метрики могут быть индикаторы на обе оси. Для каждой оси своё средневзвешенное. Если индикаторов на ось нет — значение оси = 0.0 (метрики всегда числа).

### Механика штрафа:
Для MAXIMIZE, MINIMIZE и TARGET используются:
*   `target_value` — идеал (например, 480).
*   `goal_step` — шаг отклонения (например, 60).
*   `goal_penalty` — штраф за шаг в % (например, 15).
*   *Формула:* `Оценка = 100 - (Отклонение / Шаг * Штраф)`. (Оценка не может быть ниже 0).
*   Если `goal_step = 0`, вместо шага применяется простая пропорция: для MINIMIZE — `target / fact`, иначе — `fact / target` (обе ограничены 100%).

### Типы значений (`ValueType`):
*   `NUMBER` — обычные числа.
*   `TIME` — время (08:30).
*   **`TIME_OVERNIGHT`** — время с переходом через полночь (отбой в 03:00 трактуется как 27:00, чтобы корректно вычесть цель 22:00).
*   `BOOLEAN` — логическое да/нет.

### Итог метрики:
Для каждой оси считается **средневзвешенное** по индикаторам, у которых `affects` = эта ось:
*   `satisfaction = Σ(score × weight) / Σweight` по индикаторам с `affects='satisfaction'`.
*   `attention = Σ(score × weight) / Σweight` по индикаторам с `affects='attention'`.
*   Если индикаторов на ось нет — 0.0. Если сумма весов оси = 0 — тоже 0.0 (деления на ноль нет).
*   **Вес 0 остаётся нулём** и в сервисе, и в окне «Метрика» — индикатор с весом 0 не влияет на агрегат, но из списка не исчезает.
*   **Метрика без индикаторов** тоже получает строку `metric_values` со значениями 0/0 и присутствует на графике, а не пропадает из него.
*   **Score не хранится:** в `indicator_values` пишется только факт. Сервис считает оценку при пересчёте и сразу усредняет, а окно «Метрика: {name}» пересчитывает её из текущих параметров индикатора. После правки цели/шага/веса окно показывает не те оценки, которые были учтены в сохранённой точке (TD-22).

## 7. Принятые технические паттерны

*   **Строгое разделение слоев:** SQL-запросы только в репозиториях (`*_repo.py`), бизнес-логика в сервисах, UI отдельно.
*   **Именованные параметры SQL:** Вместо `?` используются `:param_name` (словари) для защиты от ошибок порядка и инъекций.
*   **Enum для констант:** Типы целей, типы значений, методы расчета, ось влияния — в `constants.py`.
*   **Часовой пояс:** Жестко зафиксирован в `datetime_utils.py` (UTC+3). Время в БД хранится в ISO 8601 с фиксированным `+03:00` — это часть контракта БД. Литерал `+03:00` зашит не только в триггеры, но и в UI-диалоги и календарные границы `period_repo`; осознанно не исправляется (TD-18).
*   **Минутная точность:** `datetime_utils.to_minute_iso(iso)` обнуляет секунды и микросекунды, сохраняя offset. Применяется на границе записи в БД.
*   **Атомарные миграции:** `Database._apply_pending` собирает pending-миграции, выключает FK на соединении и применяет каждый скрипт как `BEGIN; … PRAGMA user_version = N; COMMIT;`. При ошибке — `rollback` и явное сообщение с именем файла и текущей версией. Бэкап делает пользователь.
*   **Автозаполнение `created_at`:** `ActivitiesRepository.add()` сам подставляет `datetime_utils.get_now_iso()`, если вызывающий код не передал `created_at` явно. При `UPDATE` поле не меняется; за `updated_at` отвечает триггер БД. Аналогично в `MeasurementsRepository` и `QuestionsRepository`. Исключение — `metric_values`: триггеров на ней нет, `created_at`/`updated_at` пишет `MetricsRepository.save_metric_value`.
*   **Порядок импорта таблиц:** `BaseExchangeService._sort_tables_for_import` использует словарь уровней FK-зависимостей: `web_time_events`=1, `regular_duties`=4, `activities`/`indicators`/`regular_duty_marks`=5, `answers`/`indicator_values`/`metric_values`=6. Костыль покрывает все текущие таблицы; универсальная топологическая сортировка — TD-09.
*   **Общее состояние дерева ролей:** `roles_tree_state` (`{str(role_id): bool}`) в `preferences`. Обновляется при `<<TreeviewOpen>>` / `<<TreeviewClose>>`. Кнопки «Развернуть/Свернуть всё» пересоздают словарь (чистят мёртвые записи).
*   **Сохранение GUI-параметров:** ширины колонок `tksheet` хранятся JSON-строкой (двойной `json.loads` — в репозитории и во вкладке), позиции разделителей — числами. Исключение: `role_links_*_col_widths` хранятся обычным списком. Ширины применяются один раз при создании вкладки и не переприменяются при обновлении данных. Мёртвые ключи в `defaults.py` не держим.
*   **Общие настройки фильтра графиков:** `chart_hidden_roles`, `chart_show_att`, `chart_show_sat` — единые для `chart_tab.py` и `chart_metrics_tab.py`.
*   **Иконка приложения в Windows:** В `app_ui.py` — `self.root.iconbitmap(default=...)` (параметр `default` критичен: без него иконка сбрасывается на «перо» при создании `Toplevel`).
*   **Форматирование периодов:** `format_period_label(mode, period)` и `MONTHS_RU` — в `ui_utils.py`. Там же — `sort_sheet_data(rows, col, asc, numeric_cols)` для сортировки tksheet-данных с уводом `None`/пустых в конец.
*   **Секреты серверной части:** `.env` (вне публичной папки, защищён `.htaccess`), `env_loader.php`.
*   **Обязательные настройки:** Если ключ в `preferences` отсутствует (`None`), сервис **падает с явной ошибкой**, а не подставляет молча дефолт. Дефолты живут только в `defaults.py`, БД получает их при `init_defaults()` (`INSERT OR IGNORE` — существующие значения не перезаписываются).
*   **EAV для измерений и опросов:** `measurement_types`/`measurement_components`/`measurement_sessions`/`measurement_values` и `questions`/`question_options`/`answers`. Компоненты типа — «атрибуты класса»; сеансы — «экземпляры»; значения — «значения атрибутов». Снимок (`answers.value`, `answers.option_description`) защищает историю от переименования варианта.
